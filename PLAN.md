# План реализации помощника менеджера для amoCRM

## Цель

Создать простой сервис для тестового задания. Он принимает обращение клиента и контекст переписки, сверяется с короткой базой знаний и выдает два отдельных блока:

1. **Ответ клиенту** — вежливый текст, который менеджер может отредактировать и отправить.
2. **Подсказка менеджеру** — уместная допродажа, обоснование и пример формулировки предложения.

**Обязательное требование: модель работает локально.** Ответы генерирует `qwen3.5:9b-q4_K_M` через Ollama на компьютере или собственном сервере. Поиск по базе знаний и вычисление векторных представлений текста также выполняются локально.

**База знаний обрабатывается по принципу RAG:** сначала поиск подходящих фрагментов, затем генерация на их основе. Даже для небольшой демонстрационной базы в модель передаются только найденные фрагменты с ограничением общего объема.

## Объем первой версии

Один экран с полем обращения, полем истории переписки, кнопкой «Подготовить ответ» и двумя блоками результата. Для первого демо менеджер вручную вставляет фрагмент диалога из amoCRM. Отправку ответа клиенту выполняет менеджер.

**Уточнение по итогам реализации:** выбран режим отдельной вкладки помощника рядом с amoCRM с ручным переносом переписки. Исходники приватного виджета и скрипт его сборки остаются опциональным расширением. Установка виджета не входит в MVP; условия установки нужно проверить для собственного аккаунта amoCRM.

## Технологии

| Компонент | Решение |
| --- | --- |
| Сервер приложения | Python + FastAPI |
| Интерфейс | HTML, CSS и JavaScript |
| Источник базы знаний | Файл `knowledge.json`, который используется при индексации |
| Поисковый индекс | Chroma с хранением фрагментов, метаданных и векторов на диске |
| Запуск локальной модели | Ollama |
| Модель генерации | `qwen3.5:9b-q4_K_M` |
| Модель для поиска по смыслу | Локальная `bge-m3` через Ollama; формирует векторы текста для поиска |
| Настройки | Адрес Ollama, имена моделей, путь индекса, количество результатов и лимит контекста |

Основной поток: **интерфейс → FastAPI → поиск в индексе → подходящие фрагменты → Qwen в Ollama → два блока результата**.

Для тестового приложения Chroma работает внутри процесса с `PersistentClient`; индекс сохраняется между запусками. При росте нагрузки его можно перенести в отдельный сервер Chroma. Такой режим локальной разработки описан в [документации Chroma](https://docs.trychroma.com/reference/python).

## Этапы реализации

### 1. Подготовить и проиндексировать базу знаний

- Собрать 10–20 записей: товары или услуги, цены, условия и ответы на частые вопросы.
- Для каждой допустимой допродажи указать, к чему она подходит и когда ее предлагать.
- Присвоить записям идентификаторы; сохранить название, тип записи (`faq`, `product`, `upsell`), товар или услугу и дату обновления. У допродаж хранить связь с основным товаром или услугой.
- Подготовить несколько диалогов с репликами клиента и менеджера.

Реализовать отдельную команду индексации:

1. Читать записи из `knowledge.json` и разбивать длинные тексты на смысловые фрагменты ориентировочно по 300–500 токенов. Короткую запись сохранять целиком; цену и условия ее применения держать вместе.
2. Вычислять векторы фрагментов локальной моделью `bge-m3` и сохранять их в Chroma вместе с текстом, идентификатором источника и метаданными.
3. При повторном запуске обновлять измененные записи по идентификаторам и хешу содержимого, удалять из индекса фрагменты удаленных записей.
4. Сохранять версию модели векторизации и настроек разбиения. При их изменении переиндексировать базу.

Индексация выполняется при загрузке или изменении базы. При обработке обращения сервер обращается к готовому индексу. Этот порядок одинаков для небольшой и более крупной базы; размер контекста модели ограничен независимо от размера базы.

### 2. Подключить локальную модель

- Установить Ollama и загрузить модель командой `ollama pull qwen3.5:9b-q4_K_M`.
- Загрузить модель поиска командой `ollama pull bge-m3`. Она используется для векторизации документов и запросов; ответы генерирует Qwen.
- Указать `OLLAMA_BASE_URL=http://localhost:11434`, `OLLAMA_MODEL=qwen3.5:9b-q4_K_M` и `EMBEDDING_MODEL=bge-m3`.
- На нескольких примерах оценить время поиска, время генерации и потребление памяти; подобрать размер контекста и предел длины ответа для выбранной модели.
- Выполнять запросы из FastAPI к локальному `POST /api/chat`, используя `stream: false`.
- Запрашивать результат по JSON-схеме с двумя строковыми полями: `client_reply` и `manager_tip`.

Интернет нужен для первоначального скачивания обеих моделей. После установки поиск и генерация должны работать локально. Выбранные модели доступны в каталоге Ollama: [qwen3.5:9b-q4_K_M](https://ollama.com/library/qwen3.5:9b-q4_K_M), [bge-m3](https://ollama.com/library/bge-m3). Локальный API и формат структурированного ответа описаны в [документации Ollama](https://github.com/ollama/ollama/blob/main/docs/api.md).

### 3. Реализовать обработку обращения

Добавить один метод приложения — `POST /suggest`.

Входные данные:

- новое сообщение клиента;
- несколько предыдущих сообщений с указанием автора: клиент или менеджер.

Порядок обработки:

1. Проверить, что обращение заполнено, и ограничить длину входного текста.
2. Сформировать поисковый запрос из нового сообщения и относящихся к вопросу последних реплик. Векторизовать его той же локальной моделью `bge-m3`.
3. Найти до пяти подходящих фрагментов для ответа. Отдельно выбрать до двух фрагментов допродаж с учетом найденного товара или услуги и связей в метаданных. Удалить дубликаты.
4. Отфильтровать слабые совпадения по порогу, подобранному на примерах. Ограничить суммарный контекст найденных фрагментов, для старта — 3000 токенов. Число результатов и лимит сделать настройками.
5. Собрать инструкцию, найденные фрагменты с идентификаторами источников и ограниченный контекст переписки в один запрос к Qwen. Текст переписки и документов считать данными для анализа.
6. Получить ответ локальной модели и проверить JSON с двумя обязательными полями.
7. Вернуть результат интерфейсу; для отладки сохранить идентификаторы найденных фрагментов и время поиска и генерации.

Если подходящих фрагментов нет, сообщить модели о нехватке сведений и сформировать уточняющий вопрос. Полная база не подставляется в качестве запасного варианта. Если индекс отсутствует или поврежден, показать ошибку подготовки базы.

Предусмотреть понятные ошибки: Ollama не запущена, одна из моделей отсутствует, поиск недоступен, превышено время ожидания или получен некорректный ответ. Пользователь может повторить запрос кнопкой.

### 4. Настроить правила генерации

**Ответ клиенту:**

- Вежливый, краткий, на русском языке.
- Цены, условия и характеристики берутся только из найденных фрагментов базы знаний.
- Если данных недостаточно — уточняющий вопрос или предложение уточнить информацию у менеджера.
- Учитываются предыдущие реплики, чтобы ответ продолжал разговор.

**Подсказка менеджеру:**

- Максимум одна допродажа из найденных фрагментов базы знаний с подтвержденными условиями предложения.
- Краткое объяснение ее пользы для конкретного клиента и пример предложения.
- Учет того, что менеджер уже предлагал и от чего клиент отказался.
- При жалобе или нерешенной проблеме приоритет — помощь клиенту.
- Если подходящей допродажи нет, прямо написать: «Сейчас допродажа неуместна».

Внутренняя подсказка выводится отдельно и не попадает в копируемый ответ клиенту.

### 5. Собрать интерфейс

- Поле нового обращения и отдельное поле истории переписки.
- Кнопка «Подготовить ответ» с индикатором загрузки.
- Редактируемый блок «Ответ клиенту» с кнопкой «Скопировать».
- Отдельный блок «Подсказка менеджеру».
- Понятное сообщение об ошибке с сохранением введенного текста.

### 6. Добавить минимальное подключение к amoCRM

Для согласованного MVP использовать отдельную вкладку с локальным помощником и ручной перенос диалога из сделки в собственном аккаунте. При работе на том же компьютере внешний доступ не требуется. Вариант ниже подготовлен в виде исходников и скрипта сборки; архив создается локально и не входит в репозиторий. Установка виджета остается за пределами MVP.

Разместить тот же интерфейс в виджете карточки сделки. Виджет обращается к серверу приложения, который выполняет генерацию через свою локальную Ollama. Размещение виджетов в карточках и обращение к собственному сервису поддерживаются [WEB SDK amoCRM](https://www.amocrm.ru/developers/content/web_sdk/start).

Для запуска внутри CRM потребуется доступный браузеру HTTPS-адрес сервера приложения. Ollama остается доступной только серверу приложения. Для демонстрации можно временно предоставить доступ к локальному FastAPI через HTTPS-туннель, ограничив доступ к нему.

Первоначально сохранить ручную вставку переписки. Автоматическое получение истории добавить после проверки возможностей конкретного мессенджера и установленной интеграции. Собственная интеграция через API чатов требует регистрации канала и публичного адреса для уведомлений — это отдельная задача, описанная в [документации amoCRM](https://www.amocrm.ru/developers/content/chats/chat-start).

### 7. Проверить демонстрационные сценарии и подготовить сдачу

Проверить:

1. Обычный вопрос — ответ соответствует базе знаний.
2. Вопрос вне базы — модель просит уточнение и не придумывает факты.
3. Подходящая допродажа — указано предложение и его польза.
4. Клиент уже отказался от предложения — оно не повторяется.
5. Жалоба или отсутствие подходящего товара — допродажа не предлагается.
6. Ollama недоступна или ответ некорректен — интерфейс показывает понятную ошибку.
7. Перефразированный вопрос — поиск находит подходящий источник по смыслу.
8. В базу добавлены нерелевантные записи — в запрос Qwen попадают только выбранные фрагменты в пределах установленного лимита.
9. Обновлена цена или удален товар — после переиндексации устаревшие фрагменты не выдаются.
10. Нет подходящих фрагментов — сервис задает уточнение; пустая выдача поиска и ошибка индекса обрабатываются отдельно.
11. После загрузки обеих моделей локальное демо выполняет поиск и формирует ответы при отключенном интернете. Работа с самой amoCRM требует сети.

Подготовить README с установкой зависимостей, загрузкой обеих моделей, командой индексации, настройками, запуском приложения и примерами обращений. Указать модели, характеристики компьютера и измеренное время поиска и генерации. Для демонстрационных вопросов зафиксировать ожидаемые источники и убедиться, что поиск их находит.

## Критерий готовности

Менеджер вводит обращение и фрагмент переписки, нажимает одну кнопку и получает два отдельных полезных блока. Ответ опирается на найденные фрагменты базы знаний, рекомендация учитывает действия менеджера в диалоге. Поиск выполняется по заранее подготовленному локальному индексу, а генерация — строго моделью `qwen3.5:9b-q4_K_M`. Объем передаваемых модели сведений ограничен независимо от размера базы.
